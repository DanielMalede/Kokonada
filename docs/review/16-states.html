Screen 16 — States

The doc board that defines every non-happy state once, so thirteen screens stop each inventing their own. The three treatments differ in what the board is for, not in how it looks.

What changed since you last saw this material

  • Four state screens already exist on the canvas as situated examples — StateLoading, StateEmpty, StateOffline, StateNoWatch, all 390×844. This board is not a fifth; it is the system behind them, the way Components is for controls.
  • There is no shipped error state. design/system/ holds Skeleton, EmptyState and OfflineBanner — and no third. The only error code in the app is playback/playbackErrorStore.ts, which is playback-specific. Every other state has a real component; this one has a hole.
  • The three real components carry constants worth printing rather than paraphrasing: SKELETON_PULSE {rest .6, peak 1, still 1}, EMPTY_GLOW_OPACITY 0.4, OFFLINE_GRACE_MS 1400, BACK_ONLINE_HOLD_MS 1600.
  • EmptyState's action is required at the type level — its source comment says this "makes a dead-end EmptyState unrepresentable". That is why empty and honest-empty must never share a component: honest-empty must have no action.
  • OfflineBanner reports visibility upward and pushes content down when shown, so every screen has two correct vertical rhythms. No artboard currently draws the second.

What I'm unsure about

  • Whether the board proposes the missing error component or just marks the hole. Proposing means designing something nobody scoped; marking means shipping a board with a visible gap. I lean toward marking — an honest gap gets chased, an invented spec gets built — but that is decision error.
  • Whether the per-screen coverage matrix belongs here. It is the most useful thing on the board and the fastest to rot: it is a snapshot of thirteen screens, wrong the moment one changes. A board that lies is worse than one that omits.
  • I think the five look-alikes are the real content. Empty, honest-empty, error, first-run and offline all render as "not much here" and mean entirely different things. If you disagree, treatment A collapses into a component index and B or C is the better spine.
  • SKELETON_PULSE.still is 1.0, so the reduced-motion skeleton sits at full opacity rather than frozen mid-pulse. Drawn that way here. Not verified on a device with the OS setting on.

Two things this table found, said plainly

  • The primary button was failing, and it was my error. It painted --brand (the fill form, #8B6FE8) behind a white label — 3.79:1 against a 4.5 floor. The token system already separates these: --brandink (#6E3FC4) is the ink form, for exactly the case where the colour has to carry text. Corrected to --brandink, now 6.62:1 light and 5.71:1 dark. Same class of mistake as the --inkbtn / accent.glowInk divergence already on the books.
  • The skeleton bar measures 1.23:1 and is marked exempt, not passed. SC 1.4.11 binds "visual information required to identify user-interface components and states". The bar is not what identifies the loading state — Skeleton carries accessibilityLiveRegion="polite" and announces "Reading your body…", and the surrounding layout is unchanged, so a user who cannot perceive the bar is still told. A skeleton is a placeholder shape, not information. This follows the standing disc-rim exemption in docs/UI_UX_OVERHAUL_SPEC.md §7.1 rather than inventing a new rule. The number is left visible on purpose — an exemption you can see and argue with is worth more than a floor quietly lowered until it went green.
