Two corrections to my own record, both in your favour

The Calm hue item is resolved. You flagged that Now Playing labelled field calm was rendering blue rather than the locked Calm hue. Enumerated now, at field=calm it paints #1F6FA6 ink over a #3FB4F0 glow in light, and #7FCDF5 in dark. That is the locked Calm pair. Fixed by the quadrant work, confirmed by measurement.

The Spotify attribution is not missing, and I was wrong to say it was. I told you no attribution component existed on mobile and listed it as a store-submission blocker to write up. experience/player/SpotifyAttribution.tsx exists and is careful: the official Full Logo PNGs (White for dark, Black for light), aspect ratio 3432:940 preserved from the asset so the mark is never distorted, height on a spacing token, the “content from Spotify” attribution line, and a link-back that foregrounds an installed Spotify or sends the user to get it. It is rendered on Now Playing at line 202, positioned between the metadata and the receipt so nothing implies Spotify authored the pick. That is not a gap; it is the reference for what the canvas should be drawing.

What is actually wrong

The board hand-draws the Spotify mark. It renders a reconstructed logo path with fill="var(--spotify)". The shipped component uses the official PNG assets precisely because redrawing the mark is not allowed. This is the same defect as the hand-drawn Apple button on Sign in, and worse here, because the correct component already exists in the repo. The board also carries the link-back label (“Listen on Spotify”) but not the attribution line — those are two different obligations and only one is drawn.

The progress bar shows a position the UI does not have. nowPlayingStore is { track, isPlaying } — no position, no duration. So “1:48”, “−3:32” and a 34% fill are drawn from nothing the screen can read. The nuance matters, though, and my earlier note got it wrong in both directions: positionMs and durationMs do arrive from the Spotify App Remote (playbackServices.ts:49), but they are consumed only by isTrackFinished() for end-of-track detection and never reach the store. So a read-only progress bar is plumbing, not fiction. A draggable one is fiction: spotifyRemoteAdapter exposes play, pause, resume, skipNext, skipPrevious, skipToIndex, getPlayerState, getTrackImage — and no seek. My earlier “3px scrub target” claim was stale; the bar is 8px and has no thumb at all.

A third hue is on screen. At every field setting the cover-art placeholder paints #9B7BF0 — brand violet — from --artph, while the fused state paints Calm. Two unrelated hues on the screen whose rule is that only the fused state is painted. I should say how this surfaced: before the colour centralisation --artph was undefined on this board, so the gradient was invalid and painted nothing. Making the token real made a latent intent visible, and the intent is wrong.

One state of several is drawn. The screen has at least playing, paused, no-track, cover-not-yet-resolved and error (playbackErrorStore). The board draws playing. It also draws two opposite-signal feedback controls 6px apart with no undo, which is a mis-tap waiting to happen on a control that trains the recommender.
