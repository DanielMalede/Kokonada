What I found on this screen

The board offers three ways in. The product has two, and on Android it has one. src/auth/auth.ts exports exactly signInWithGoogle and signInWithApple — there is no email sign-in anywhere in the module. The “Continue with email” button is an action the app cannot perform, on the screen whose entire job is to perform it. SCREENS.md §3 lists an “email flow” too, so the doc is wrong alongside the canvas.

Apple is drawn on an Android-first board where it never renders. SignInScreen.tsx:48 gates it: Platform.OS === 'ios' && appleAuth.isSupported. On our first shipping target the screen has one button. Two of the three drawn are wrong for the platform we ship first — which is also why the “313px of empty flex” reads worse than it measures: the stack was padded with buttons that do not exist.

Both provider marks are dashed placeholders that were never replaced. The shipped code uses Apple’s official AppleButton (ASAuthorizationAppleIDButton) and says so in a comment — “never a hand-drawn look-alike” — because HIG requires it. A hand-drawn Apple or Google button is a store-rejection surface, not a taste question. In the frames below both marks are represented, not reproduced: correct measure, correct fill, placeholder glyph. Dropping in the official assets is the compliance-auditor’s gate, and I have not treated it as design work.

Correcting my own record. I told you earlier that Login was the one pre-emotion board rendering no accent. That was wrong. Enumerated from computed styles, it paints #4B6FD0 (chroma 133) as a gradient stop in the top wash, in both themes — the same defect as Onboarding. Five pre-emotion boards were affected, not four. Every frame below is achromatic.

Zero of the four states are drawn. SCREENS.md §3 specifies idle · submitting · error · success, and the shipped screen implements a real inline error with accessibilityRole="alert" and a busy state that dims both buttons to 0.6. The board draws idle only. The State row below draws the other two.

The legal line is text, not a link. “By continuing you accept the Terms and the Privacy Notice” has no target and no affordance, so the two documents it names are unreachable from the screen that binds you to them. Separately I checked the claim beside it — “free, with no ads and no paid tiers” — against docs/adr/0001-100-percent-free-app.md, which is Accepted and locked. That one is true and it stays.

Carried forward, and what I want your eye on

Your Splash choice reaches this screen. You picked wave alone with mark travels, so the thing arriving here is the wave — but this board still draws the ring-and-wave lockup, which Splash no longer has. That is a cross-screen break created by the Splash decision, not a pre-existing one. The Mark row resolves it; wave is what continues the handoff.

One question I am not deciding for you: is red allowed here? The error state uses state.danger — a token that is declared in tokens.ts (#B4322F light / #FF9BA0 dark) and measures 5.87:1 and 9.50:1, so it is contrast-clean. But this is a pre-emotion screen under an achromatic rule. My read is that the rule governs the accent — the emotion colour — and that a declared error token is a different axis, so red for a genuine failure is fine. Set State to error and tell me if you disagree; if you do, the alternative is a neutral alert carrying the failure by border and weight alone.

The promise line differs between the board and the app. Shipped copy is “Music that moves with your body and mood.” The board says “Sign-in never asks for health data. That comes later, and it’s optional.” Both are defensible and they argue different things — one sells, one reassures. That is the Promise row, and it is a real fork, not a tidy-up.

Fonts. System faces, because this file runs offline. The real screen uses General Sans for headlines; tracking and letterform will differ, proportions will not.
