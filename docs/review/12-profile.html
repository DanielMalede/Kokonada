The finding that outranks the others

“Withdraw health consent” and “Delete my account” are unreachable in the drawn flow. They exist — on YouVault.dc.html, drawn properly, with an IRREVERSIBLE label. But no screen board navigates to that board. I checked all 22: only Plan.dc.html (a documentation board) and the Vault itself mention it, and the Flow board does not route to it either. Profile’s YOUR DATA section contains exactly two rows: Export everything and Log out.

The shipped app already does this correctly — it is the canvas that is behind. An independent verification pass confirmed it at high confidence: ProfileScreen.tsx:354-358 renders “Delete account” unconditionally, behind a two-step confirm at :361-383; withdrawal renders through VaultConsentPanel (mounted at :327-333), with its own neutral two-step confirm — “Keep it” / “Withdraw” — and it appears only when consentGranted is true. So the board is not ahead of the product; it is behind it, and the product is the reference for what the board should draw, including that conditional.

Your Stage 2 requirement was that these “come back as real, reachable actions in the markup — not fit by trimming copy elsewhere.” They came back as markup on a board with no door. That is a different failure from the original one, and it is arguably worse, because it looks solved. Row one is where they live.

Two controls that do not exist

The Living background toggle is not built — but persisting it is solved. There is no ambient-field setting anywhere (livingBackground, fieldEnabled, auraEnabled, backgroundEnabled all return nothing). I first wrote that mobile had no settings-persistence layer; that was wrong twice over. The sanctioned path is SecureStore (storage/secureStore.ts:19 — “the only sanctioned persistence path on the device”) over a KVBackend port, encrypted MMKV plus a cipher in production. And there is already a three-instance pattern for persisted toggles under the koko. namespace — koko.liveMode, koko.onboarding.seen and koko.connect.<uid>.resolved — each a zustand vanilla store with hydrate() bound in prodBootstrap.ts. So this is not an architectural question at all: there is an exact precedent to copy. Worth knowing that the live-mode switch on Generate is currently the only toggle in the whole app, so this would be the second. The board currently shows a switch that cannot be switched.

The “HOW ADVENTUROUS” slider is not unbacked — it is counter-backed, which is worse. My first search said no such parameter existed. That was wrong, and I re-ran it before writing this. backend/app/agents/runtime/knowledge/noveltyController.js is a Thompson-sampling bandit that decides exactly this, per context bucket — {stateDomain, targetBand, hourBin} — because the trade-off is contextual. The file argues the point directly: “the same person who welcomes an unknown track on a Sunday morning skips it three times in a row mid-interval”, and a fixed draw is “noise wearing exploration’s clothes.” It also abstains entirely until it has an observation, so it never guesses. Its cap is MAX_NOVELTY_SHARE = 0.3 — which is where the board’s “about a third of each set” comes from. So the copy is right and the control is the problem: a user-set dial would override a learner built specifically to be context-sensitive, and would replace something that abstains when ignorant with something that always has an opinion.

What I measured

The preview box is empty, and I can tell you exactly why. It renders 314×42 with three children, two of which do paint — so it is not missing markup. The field layer is .fld1 { bottom:-40%; height:150% } and its gradient origin is at 50% 100%. In a 42px box that puts the bright core of the gradient roughly 17px below the visible area. The geometry is percentage-based and tuned for an 844px screen; dropped into a 42px preview it aims its light off-stage. A preview of the living field has to be drawn for its own box, not inherited from the screen.

The toggle is 50×30. Below the 44px floor, on the only switch in the app.

Three hues on screen. #3A5CCC nine times (toggle fill, slider fill, slider knob border) — the same undeclared blue you named; #4B6FD0 in the field preview; #9B7BF0 on the mini-player artwork. Worth being exact about the objection: the blue passes contrast at 5.86:1 and 5.63:1. It is an undeclared-token problem, not a legibility one.

Content is not clipped; it scrolls. 681px box over 846px of content — 80% visible, with a bottom fade. The 20% below the fold is the whole YOUR DATA section, which is where the account actions would live.
