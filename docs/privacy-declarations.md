## Retention

| Data | Retention | Mechanism |
| :--- | :--- | :--- |
| Biometric samples (`BiometricLog`) | **90 days** (default; `BIOMETRIC_RETENTION_DAYS`) | MongoDB TTL index on `recordedAt`. |
| Authoritative Apple HealthKit samples and deletion tombstones (`HealthSample`) | **90 days** maximum from server receipt | MongoDB absolute TTL index on `expiresAt`. Active rows expire at the earlier of 90 days after the sample ends and 90 days after server receipt; tombstones expire 90 days after receipt. Physiological values are field-level encrypted. Internal keyed identities (`sampleKey` in this store and `healthSampleKey` in derived projections) are omitted from the subject-facing export. |
| HealthKit ingest operation journal (`healthingestbatches`) | Renewable active-write lease: **5 minutes**; terminal record: until the request or next five-minute repair pass removes it | Contains no physiological value. The writer renews and verifies ownership before and after each sample mutation. A batch is marked complete only after every operation is staged; an expired incomplete batch is aborted and its staged prefix is removed. The repair pass also scans staged rows independently and removes any whose journal is absent, covering a writer that resumes after its lease was reaped. One fixed-size record exists per in-flight request and is deleted after commit or verified abort. |
| Health projection cleanup journal (`healthprojectioncleanups`) | Until projection success or verified compensation; retried by the five-minute repair pass | Contains no physiological value. It is deliberately not erased with the `User` document because it is the deletion obligation that removes a projection written late by an already-running request. Cardinality is bounded to one marker per user/provider/connection generation, and each marker is capped at 2,000 keyed sample identities. Projection writers renew and verify ownership around every mutation. Recovery claims an expired active marker, cleans once, retains it for one additional grace lease, and cleans again before deletion. Because elapsed time cannot prove that a suspended writer has stopped, every repair pass also independently removes linked biometric and vital projections that no longer have a matching active, committed authoritative health sample, and clears stale Apple-owned medical-profile provenance without deleting unrelated legacy or manual fields. A time-based TTL is intentionally not used because expiring an unfulfilled deletion obligation would leave health data orphaned. |
| Per-metric physiological samples (`VitalSample`) | **90 days** (default; `VITAL_SAMPLE_RETENTION_DAYS`) | MongoDB TTL index on `recordedAt`. Field-level encrypted per ADR 0005; erased with the account and by per-wearable disconnect, and included in the subject's export, on the same rails as `BiometricLog`. |
| Nightly consolidated readiness/sleep-debt/cosinor/CUSUM history (`MorningState`) | **90 days** (default; `MORNING_STATE_RETENTION_DAYS`) | MongoDB TTL index on `date`. Field-level encrypted per ADR 0005; erased with the account and (all-or-nothing, alongside `MedicalProfile`) by per-wearable disconnect, and included in the subject's export. |
| Learned context-bucket rewards (`RewardEvent`) | **365 days of INACTIVITY** (default; `REWARD_EVENT_RETENTION_DAYS`) | MongoDB TTL index on `updatedAt` — the window is a staleness eviction, not a deletion clock: every play in a context pushes that bucket's expiry out, so what expires is only learning about a context the person has left. Not encrypted and deliberately so: the row holds outcome statistics (`rewardSum`, `count`) addressed by COARSE coordinates (one of six state domains × one of three target bands × one of four six-hour bins) — no vital, no state label, and no track identity of any provider (ADR 0012 §1). Erased with the account, erased when a user who had granted health-data consent withdraws it ([ADR 0015](adr/0015-withdrawal-erases-learned-personalization.md)), and included in the subject's export; NOT erased by per-wearable disconnect, because a bucket's evidence is half behavioural and its state coordinate resolves without a wearable at all. |
| Learned scoring overlay (`PersonalWeights`) | **365 days of INACTIVITY** (default; `PERSONAL_WEIGHTS_RETENTION_DAYS`) | MongoDB TTL index on `updatedAt` — a staleness eviction on the same footing as `RewardEvent`: every observation pushes the expiry out, and what expires is an overlay nobody has reinforced for a year. Expiry is not a loss here — a missing row means COLD START, i.e. the deployment-default scoring weights, which is exactly where the §M.15 shrink-to-global was taking it anyway. Not encrypted and deliberately so: the row holds four bounded music-RANKING coefficients (how much this listener's ranking leans on their own affinity vs. biosonic fit vs. genre vs. proven rotation) — no vital, no state label, no track identity of any provider, and no way to invert one out of a ±0.4 residual shared across every play. Erased with the account, erased when a user who had granted health-data consent withdraws it ([ADR 0015](adr/0015-withdrawal-erases-learned-personalization.md)), and included in the subject's export; NOT erased by per-wearable disconnect, for the same reason `RewardEvent` is not — half the evidence behind it is behavioural (skip / complete / save), which no wearable ever touched. |

- **Disconnect Spotify:** Profile → Spotify → **Disconnect**, then confirm. ## GDPR Art.9 consent (health/biometric processing)

- OS/OAuth read grants alone are **not** lawful Art.9 consent. A dedicated, versioned, explicit consent record is captured and enforced server-side: special-category ingestion endpoints are hard-gated by `requireConsent('health_biometric_processing')`, and a stale/absent/withdrawn consent blocks ingestion. <!-- verified: backend/app/routes/integrations.js:21-24,79,83; backend/app/models/ConsentRecord.js:5-12,45-47 -->
- A user-facing **consent screen** presents purpose, data types, retention, sub-processors, and the withdrawal path, and writes the versioned `ConsentRecord` — shown just-in-time immediately before the OS Health Connect permission prompt (`docs/design-v1/screens.md` §11). Withdrawal is a new append-only `withdrawn` row and revokes future ingestion. Before it answers, it also erases the wearable data footprint; the learned preferences (`RewardEvent`, `PersonalWeights`) and the learning jobs and state recompute jobs waiting in the job queue (`bull:reward-ingest:`, `bull:state-vector-recompute:`), when a grant was on file; and, for a user who granted health-data consent before the withdrawal, the heart-rate snapshot kept on each session, the values derived from it on each session and serve event, and the user-scoped cache (see **Retention** for each). A session or serve event that a generation already running writes after the withdrawal is cleared once it lands, and a step that did not finish is completed by the daily `sessionTrim` job (`healthErasures=`). History keeps each session (see **Retention** for what it keeps). Withdrawal does not remove: the free text a user typed, which keeps its own clock (removed before the session is 31 days old); the tracks of a heart-rate session and of its serve events, which keep theirs (see **Retention**); the mark that a session was Live; an activity chip on a session that never held a heart rate and is not past the 30-day trim, a chip-only activity on an older session, and any activity on a session made after the withdrawal that holds no heart rate (see **Retention**); a learning job already running when the withdrawal is made, queued by a play that ends while it is processed, or waiting while the job queue cannot be reached or does not answer in time, each deleted by the job queue once it has run, and what such a job writes to the learned preferences, which then follows their own retention (see **Retention**); the entries naming the user's state recompute jobs by a pseudonym in the job queue's event log, which the daily `sessionTrim` job deletes within 2 days; what a state recompute job already running when the withdrawal is made writes if the server stops before it checks consent again, or its undo fails: the profile, which has no retention limit of its own and which the nightly analysis keeps processing, writing `bio:baseline:` again and adding a `MorningState` row each night, and the `bio:affect:` key until it expires (2 hours) (see **Retention**; `BE-027`, `BE-029`); a `bio:affect:` key that a heart-rate reading already being processed writes again (it expires within 2 hours), and a candidate pool (`pool:`) left by a playlist generation already running that then fails (it expires within 12 hours by default); and application logs and any database backups, which follow their own retention.
- **H-9 is now fully closed across every user-facing ingestion path.** All three special-category ingestion routes are consent-gated: `/apple/push` and `/health/batch` via the session-authed `requireConsent` middleware; `POST /integrations/watch/hr` (the device-token-authed live BLE heart-rate lane — previously the one gap, since it has no session `req.user`) via an inline check on the same `getConsentStatus` service against its already-resolved token→user lookup, running BEFORE any body validation or socket delivery. <!-- verified: backend/app/controllers/integrationsController.js watchHrIngest (getConsentStatus gate, resilience-audit follow-up); backend/tests/watchIntegration.test.js "Art.9 consent gate" (5 tests) --> `POST /integrations/garmin/webhook` remains genuinely not yet reachable, pending Garmin Health API production approval (separate Pause & Guide human gate) — not a live gap, since no traffic flows there today.
- **Cross-package version integrity:** the mobile client declares which contract version (`CONSENT_SCREEN_VERSION`) its consent copy/data-categories represent on every grant; the server rejects (409 `stale_client`) a mismatch rather than silently recording an un-updated app's grant as "current." This closes a residual gap where a server-only `CURRENT_CONSENT_VERSION` bump could otherwise let an old app's grant read as consented to terms it never displayed. <!-- verified: backend/app/services/privacy/consent.js recordConsent clientVersion check; mobile/KokonadaHealth/src/health/consentApi.ts CONSENT_SCREEN_VERSION -->
