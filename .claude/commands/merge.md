POST-MERGE (after `gh pr merge`, the MCP merge, or a merge from the GitHub UI):
1. FACTS. `gh pr view <n> --json number,url,state,mergedAt,mergeCommit,headRefOid,baseRefName`; `git fetch origin`. S = `mergeCommit.oid`, H = `headRefOid`. `git merge-base --is-ancestor "$S" origin/main` must exit 0 (S is on main). A base other than main: `RED (UNVERIFIED)`, no CI ran for it (`OPS-011`). `mergeable` reads UNKNOWN on a merged PR; ignore it. `mergedAt` inside 02:58-05:10 UTC is a finding (`OPS-110`) to record, not a factor in the result: waiting cannot undo it.
2. CONTENT EQUALITY. `git diff --quiet "$H" "$S"` must exit 0 - squash merges have stranded commits before. Non-zero: `RED (CONTENT-MISMATCH)` with `git diff --stat "$H" "$S"`. Then diagnose, which informs the fix and does not change the result: P = S's first parent (`git rev-list --parents -n 1 "$S"`). If `git merge-base --is-ancestor "$P" "$H"` exits 0, H already held main, so the difference is content the PR never had or content it lost: stranded or extra commits, unambiguous. If not, compare `git diff "$(git merge-base "$P" "$H")" "$H" | git patch-id --stable` with `git diff "$P" "$S" | git patch-id --stable`: equal ids mean the squash carried exactly the PR's change onto a main that had moved (S is a tree no PR gate saw): the result stays `RED (CONTENT-MISMATCH)`, say that CI on S (step 3) is the gate, and this case never counts toward the Rule-of-2 revert below; different ids mean the merge carried something else. S with two parents is a merge commit, not a squash (#218 was one): say so; this repository merges by squash (step 4 of the flow above).
3. MAIN CI ON S. `gh run list --workflow CI --branch main --commit "$S" --json databaseId,status,conclusion,headSha,event`; wait until completed (`gh run watch <id> --exit-status`); no run after about 3 minutes of re-listing: `RED (UNVERIFIED)`. Require success, and apply PRE-MERGE 3d-3f and 4 to S (`commits/$S/check-runs`; on a push to main the paths-filters compare S with the previous main), leaving out the check run `gitleaks — full history`, which belongs to `Secret scan (full history)` (step 4); 3f's owner-accepted neutral does not apply to S: it names a PR's H and its record.
4. ONLY THE `CI` WORKFLOW COUNTS. Report the latest `Secret scan (full history)` separately (`gh run list --workflow "Secret scan (full history)" --limit 1 --json conclusion,createdAt,headSha`); it is never part of the result.
5. THE WHOLE OF MAIN. `git fetch origin`; T = `git rev-parse origin/main`. `gh run list --workflow CI --branch main --event push --limit 20 --json databaseId,headSha,status,conclusion,displayTitle,createdAt`: the run for T must be completed + success - await it if it is running; a tip with no CI run (a `[skip ci]` commit) is `RED (UNVERIFIED)`. This is how a merge from the GitHub UI that bypassed every gate gets caught. If it is red, walk back to the oldest failing run after the newest green one: its `headSha` is the commit that turned main red. Name its PR (`gh pr list --state merged --search <sha> --json number,title`, or `gh api "repos/{owner}/{repo}/commits/<sha>/pulls"`); no PR means a direct push to main - say so. `RED (FAILING)`: "main red since <sha> (PR #x)", with that run's `--log-failed` evidence.
6. ALWAYS NOT EXERCISED: the deployed build. A merge to main starts a Railway deploy before CI ends, and `/health` carries no commit sha (`OPS-018`), so the session cannot confirm production runs S; Wait for CI on the backend service is the owner's step (`DAN-053`).

THE RESULT. GREEN only when every step of the phase established its fact. Several reasons: list every tag, most severe first - CONTENT-MISMATCH, FAILING, CONFLICT, APPROVAL, DIFF, UNVERIFIED, WINDOW. The result is bound to H and M: a push after it voids it (the session runs PRE-MERGE again on the new head), so does main moving past M, and the merge must use `gh pr merge <n> --squash --delete-branch --match-head-commit <H>` (step 4 of the flow above).

THE RECORD. The session posts the result as a new PR comment, from a UTF-8 file with LF line endings and no BOM (`gh pr comment <n> --body-file <file>`): English, terse, no praise. Its first line is `PRE-MERGE CHECK <GREEN | RED (<TAG>[, <TAG>...])> @ <H> on <M>`, or after a merge `POST-MERGE CHECK <GREEN | RED (<TAG>[, <TAG>...])> @ <S>`; then, in this order:
PR: #<n> <url> · base <base> · phase <pre-merge|post-merge> · checked <UTC time>
H: <sha> · M: <origin/main sha>   (post-merge also) S: <sha> · content <equal | differs: stat>
CHECKS on <H|S> (run <id>): one line per check - <name>: <conclusion>
NOT EXERCISED: one line per gap, e.g. "Android compile: steps skipped by paths-filter - not compiled (OPS-010)"
FINDINGS: <TAG> <file:line | job name> - what; then the trimmed `--log-failed` lines
WARNINGS: window-time merge, console.log to justify
NEW-FINDING: anything out of scope the session noticed, one line each

ON RED. The session records each finding as a TASKS.md row (the next free ID from its header, or an update line on the row it belongs to), fixes it before the next task (DEC-143) and runs the check again on the fixed state. Two consecutive post-merge RED results for the same merge - a RED, a fix, RED again - and the session opens a revert PR of S (Rule of 2, `docs/ORCHESTRATOR_FABLE.md` `<error_budget>`): a branch and a PR into main, never a push to main, never force; only for a content mismatch with different patch-ids or a red CI on S, never for equal patch-ids alone. A `RED (APPROVAL)` whose only cause is a missing or stale approvals record is not a finding either: no TASKS row; the fix is to run `/review-pr`. `RED (WINDOW)` alone is not a finding: no TASKS row; no merge before 05:11 UTC; run the check again before merging. A RED caused only by the environment (`gh` missing or unauthenticated, `git fetch` failing) is not a finding either: no TASKS row; it means only "do not merge from this environment". Such a RED, and equal patch-ids with CI on S green, cannot become GREEN by any fix: the session notes it and goes on, and never loops on it.
