THE 16 KB CHECK — Play's 16 KB page-size requirement. The owner's phone (a Galaxy S22+) cannot boot with 16 KB pages, so `/page` G11P never carries it, and an emulator image with 4 KB pages proves nothing about it. Static, on the exact release artefact, before every upload and on the cutover head's release build, run by the developer, whose raw output, with the artefact's SHA-256 (`sha256sum <artefact>`), is among G12F's inputs: `zipalign -c -P 16 -v 4 <apk>` passes (build-tools 35 or later); the ELF checks run on every 64-bit native library: an APK's `lib/arm64-v8a/*.so` and `lib/x86_64/*.so`, and an app bundle is checked through `bundletool build-apks --mode=universal --bundle=<aab> --output=<apks>` and the universal APK it holds, or through its `<module>/lib/arm64-v8a/*.so` and `<module>/lib/x86_64/*.so` paths, `base/` included; a run that reads zero `.so` files for a 64-bit ABI the artefact ships is RED. Each library has every ELF `LOAD` segment aligned at `2**14` or more (`llvm-objdump -p <so>`) and meets Google's RELRO rule, read with `llvm-readelf -Wl <so>`: the library has no `GNU_RELRO` segment, or that segment's `VirtAddr` plus its `MemSiz` is a multiple of 16384, or it ends exactly where the `LOAD` segment that holds it ends. An app bundle's config names `PAGE_ALIGNMENT_16K` (`bundletool dump config --bundle=<aab>`). Runtime, at `/page` G11e: the release build installs and runs on an AVD made from the 16 KB-page image `system-images;android-35;google_apis_ps16k;x86_64` ("16 KB Page Size Google APIs Intel x86_64 Atom System Image"), whose manifest records that `adb -s <serial> shell getconf PAGE_SIZE` prints 16384. First `adb -s <serial> shell setprop bionic.linker.16kb.app_compat.enabled false` and `adb -s <serial> shell setprop pm.16kb.app_compat.disabled true` turn off the compatibility mode that would hide a misaligned library; then the check passes only if each page opens and logcat shows no `dlopen` or `SoLoader` error.
